# Как работать с Agent Mode (Arena AI) максимально эффективно

**Контекст:** разработка / доработка / багфикс игры. Агенту открыт полный доступ к репозиторию (доки + код). Файлов много — задача: чтобы в контекст агента попало **именно нужное**, а не «всё из репо».

Метод собран из: стандарта [AGENTS.md](https://agents.md), best practices Anthropic (Claude Code), исследования Augment Code по AGENTS.md (июнь 2026), «Agent Experience» Marmelab (январь 2026) и документации/changelog Arena AI.

---

## 0. Как это устроено: с чем боремся

- У агента есть **контекстное окно**. Всё, что он прочитал (файлы, поиск, вывод команд, ваши сообщения), лежит в нём и расходует бюджет.
- Чем длиннее сессия, тем хуже результат. По наблюдениям сообщества (claude-code-best-practice): деградация («dumb zone») начинается при заполнении контекста ~30–40%, после 60% ошибки растут заметно. В Arena AI длинные чаты **автоматически компактируются** (начало разговора заменяется саммари), а в саммари теряются детали.
- Главные рычаги, в порядке важности:
  1. **Меньше нужно читать** — структура репо, компактные доки, минимальные комментарии.
  2. **Читать только нужное** — индекс доков, прогрессивное раскрытие, точные промпты.
  3. **Один чат = одна задача** — новый чат это «очистить контекст».
  4. **Состояние хранить в файлах, а не в чате** — переживает компактацию.
  5. **Агент должен уметь проверить себя** (тесты/build в песочнице).

---

## 1. Ключевые принципы

1. **Один вход в знания — `AGENTS.md` в корне.** 100–150 строк, императивный, с точными командами.
2. **Документация = карта, не энциклопедия.** Агент читает оглавление (индекс), а не все доки.
3. **Прогрессивное раскрытие:** `AGENTS.md` → `docs/INDEX.md` → док подсистемы → код. Каждый уровень даёт ровно то, что нужно, чтобы решить, куда идти дальше.
4. **Верификация — самый сильный рычаг качества.** Если агент может запустить тесты/сборку и сам увидеть провал — качество резко растёт.
5. **Сначала план, потом код.**
6. **Исправлять контекст, а не только результат.** Каждый раз, когда вы поправляете агента, правило попадает в `AGENTS.md`/доки.
7. **Один источник правды.** Доки не дублируются: ссылки, а не копии.

## 2. Куда положить базовую инструкцию

### Выбор файла

| Вариант | Вердикт |
|---|---|
| **`AGENTS.md` в корне** (именно так: множественное число, капсом, без точки) | ✅ **Да.** Де-факто стандарт: поддерживают Claude Code, OpenAI Codex, Cursor, GitHub Copilot, Jules, Zed, Aider, Windsurf, Devin и др. (60 000+ примеров на GitHub). Одна инструкция работает для всех инструментов. |
| `agent.md`, `.agent`, `.agent.md` | ❌ Нет. Не стандарт — ни один агент не подхватит его автоматически. На Linux регистр имеет значение: `agent.md` ≠ `AGENTS.md`. |
| `CLAUDE.md` | Только если параллельно пользуетесь Claude Code: сделайте его **символической ссылкой** на `AGENTS.md` (или наоборот). Два независимых файла = рассинхрон. |
| Доки в `docs/` | Да, но как «референсы», на которые ссылается `AGENTS.md`. |

### Особенности Arena AI Agent Mode

- Подключение репозитория: **интеграция с GitHub** (доступна с 26.08.2026) — агент работает с репо напрямую: коммитит, пушит, открывает PR, есть панель диффов. Это самый чистый путь.
  - Если репо не на GitHub: загрузите zip исходников **без** `.git/` и бинарных ассетов (раздел 6).
- Файлы workspace сохраняются между сообщениями в чате; готовые артефакты можно скачать.
- Автозагрузки `AGENTS.md` в Agent Mode нет (в отличие от терминальных агентов из списка выше), поэтому **делайте две вещи**:
  1. Положите `AGENTS.md` в корень репо (он же пригодится другим агентам).
  2. Начинайте каждую задачу **бутстрап-промптом**: «Начни с чтения `AGENTS.md` и `docs/INDEX.md`».

### Рекомендуемая иерархия

```
repo/
├── AGENTS.md              # ≤ 150 строк: команды, соглашения, границы, оглавление доков
├── README.md              # для людей (агент может читать, но это не главный источник)
├── docs/
│   ├── INDEX.md           # оглавление: док → 1 строка о содержимом (≤ 60 строк)
│   ├── architecture.md    # карта систем, ≤ 150 строк
│   ├── combat.md          # один док = одна подсистема
│   ├── inventory.md
│   └── ...
└── src/
    └── combat/
        └── AGENTS.md      # (опционально) правила модуля — читается при работе в нём
```

Субдиректорные `AGENTS.md` — для больших модулей с особыми правилами: они не раздувают корневой файл, а подгружаются, когда агент уже «в теме».

## 3. Как сформулировать базовую инструкцию (`AGENTS.md`)

### Правила формулировки

- **Императив и конкретика.** Не «мы предпочитаем pnpm», а «Используй pnpm, не npm».
- **Команды — точные, с флагами.** Самый высокий ROI-раздел: агент, который не может запустить тест/сборку, начинает гадать.
- **Show, don't tell.** Указать пример-файл из кодовой базы лучше, чем описывать паттерн словами.
- **Границы Always / Ask First / Never** — на всё, что агент может сделать от своего имени.
- **Без воды.** «Пиши чистый код» — ноль пользы. Если агент и так делает правильно без инструкции — удалите её (over-specified AGENTS.md заставляет игнорировать половину файла).
- **Размер: 100–150 строк — сладкая точка.** По данным исследования Augment Code, длинные файлы дают отрицательный эффект. Абсолютный потолок — 500 строк, но стремиться не к чему.
- **Язык:** шаблон ниже на английском — экономнее по токенам и «роднее» для моделей. Русский тоже работает, но англ. предпочтительнее.
- **Версии фиксируйте.** Без пингов агент дрейфует к самым частым паттернам из обучения.

### Шаблон (адаптируйте)

```markdown
## Project
<2–3 предложения: что за игра, жанр, движок+версия. То, что нельзя
вывести из кода: «мы сознательно используем X, а не Y, из-за ...».>

## Stack
| Что | Версия |
|---|---|
| Движок | Godot 4.3 |
| Язык(и) | GDScript, C# |
| Ветвление | Git, conventional commits |

## Commands
- Запуск (dev): `...`
- Тесты: `...`  # обязаны быть зелёными перед коммитом
- Lint/формат: `...`
- Headless smoke-тест: `godot --headless -s tests/smoke.gd`

## Architecture (карта, ≤ 10 строк)
- `src/core/` — игровой цикл, управление сценами → док: docs/architecture.md
- `src/combat/` — бой: только тут, нигде больше → док: docs/combat.md
- Правила: сигналы только через EventBus; сетевой код — только в `src/net/`

## Conventions
- Код самодокументируется. Комментарий — только для неочевидного «why»
  (workaround, квест-физика, business-правило, ссылка на баг/тикет).
  Комментариев, повторяющих код, — НЕТ. Закомментированного кода — НЕТ.
- Файл < 300 строк; разбиение по ответственности.
- Именование: `...`
- Перед созданием нового класса/функции — поиск похожего (grep).
  Колёса не изобретать.
- Паттерны: стейт-машины — `StateMachine<T>` из `src/core/state.gd`
  (пример: `src/combat/fighters/skeleton.gd`).

## Boundaries
### Always
- Запускать тесты и lint перед коммитом.
- Обновлять док подсистемы, если изменился контракт.
- Маленькие коммиты: один коммит = один логический шаг.
### Ask first
- Изменение формата сейва / данных.
- Новые зависимости.
- Удаление файлов, изменение публичного API.
### Never
- Коммитить ассеты/ключи/.env.
- Force push.
- «Исправлять по пути» код вне заявленной задачи.

## Gotchas (≤ 10 пунктов)
- Delta time — в мс, не секундах (вся физика на мс).
- ...

## Definition of Done
[ ] тесты+lint зелёные  [ ] без новых предупреждений
[ ] док обновлён (если менялся контракт)  [ ] коммит с понятным сообщением
```

## 4. Документация: как устроить, чтобы помещалась в контекст

- **`docs/INDEX.md` — главный документ.** Таблица: док → одна строка о содержимом. Агент читает индекс (~1k токенов), а не десять доков (~50k).
- **Один док = одна подсистема**, 50–150 строк. Отвечает на: что тут живёт, как связано, каковы контракты (API/данные), где грабли. Не «как всё работает в целом» — это видно из кода.
- **Прогрессивное раскрытие:** в `AGENTS.md` — по одной строке на док (не более 10–15 ссылок); в доке — ссылки на следующий уровень, если он есть.
- **Ловушка переисследования (over-exploration):** расплывчатые описания архитектуры заставляют агента «для надёжности» читать всё подряд — в исследованиях полнота результата падала на ~25%. Пишите **границы**: «логика боя — только в `src/combat/`, не ищи её в других местах». Чем точнее «что где», тем меньше блуждания.
- **Доки = часть кода:** обновляются в том же PR, что и изменение (правило в `AGENTS.md`). Устаревшая док хуже её отсутствия — агенту верят.
- **Не держите в репо мёртвые спеки и черновики.** Агент находит и читает их, даже если они не в индексе. Архивировать или удалять.
- README — для людей. Не ждите, что агент сам догадается, что главная док в README.

## 5. Комментарии в коде: минимизировать

**Ответ на вопрос «много или мало»: минимально.** Почему:

- Каждый файл, который читает агент, идёт в контекст. Комментарий — это «мертвый» вес поверх кода: код 300 строк + комментарии 150 строк = в два раза больше читаемого.
- **Агент сам любит расставлять избыточные комментарии** (известная привычка, зафиксирована в гайдах по agent experience). Без явного запрета репо разрастается комментарием с каждой сессией.
- Самодокументируемый код и стандартные паттерны (стейт-машина, ECS, observer) агент понимает **быстрее**, потому что «знает» их, а не читает описание.

**Правило в `AGENTS.md` (готовая формулировка):**

> Comments: never add a comment that restates what the code says.
> A comment is justified only for a non-obvious *why*: a workaround, a
> physics/engine quirk, a business rule, a link to a bug/ticket.
> No commented-out code. No "TODO: maybe later" without an issue link.

**Связанные практики:**

- **Дробить большие файлы** (предел ~300–500 строк). Агенты часто читают файлы частями; огромный файл = несколько чтений = раздувание контекста.
- **Логика отдельно от движка** — см. раздел 11: это же нужно для тестов.

## 6. Что НЕ должно попадать в контекст агента

- **Бинарные ассеты** (текстуры, модели, звук): лучше вне репо (облако/CDN) или Git LFS. Агент не может «прочитать» 50 МБ текстуры, а при загрузке zip-ом они раздувают архив.
- **Сборки, minified-код, generated-файлы:** в `.gitignore`, никогда не коммитить.
- **Крупные данные** (спreadsheets, дампы сейвов, логи): не в репо (или в архиве вне истории).
- **`.git/`** при загрузке zip-ом — не включать.
- **Правило:** в репо должно быть только текстовое, что агент реально использует в работе.

## 7. Как формулировать задачи (промпты)

### Общие правила

- **Один чат = одна задача.** Новая задача → новый чат.
- **Бутстрап-промпт в начале:** «Ты работаешь в репо <игра>. Начни с чтения `AGENTS.md` и `docs/INDEX.md`.»
- **Ограничивайте область:** какие файлы/каталоги, какие сценарии.
- **Указывайте на паттерны:** «посмотри, как сделано в `src/inventory/`, повтори структуру».
- **Симптом + что значит «исправлено»** (для багов).
- **Требуйте верификацию:** «запусти тесты, покажи результат».
- **«НЕ делай X»** работает не хуже «делай Y».

### Шаблон — багфикс

```
Ты работаешь в репо <игра>. Начни с AGENTS.md и docs/INDEX.md.

Баг: <симптом в 1–2 предложения>.
Как воспроизвести: <шаги>.
Где смотреть: <каталог/файл — или «найти самому; начни с grep по "X"».
Исправлено = <что должно происходить вместо этого>.
Ограничение: минимальное изменение, без рефакторинга «по пути».
Верификация: воспроизвести ДО и ПОСЛЕ + тесты зелёные.
```

### Шаблон — новая фича

```
Ты работаешь в репо <игра>. Начни с AGENTS.md и docs/INDEX.md.

Цель: <одно предложение>.
Ограничения: <что не должно меняться; куда должен попасть код>.
Паттерн: следуй <пример-файл> — та же структура и соглашения.
Не делай: <запреты>.
Верификация: <тесты/smoke> + <как проверить в игре>.
```

### Шаблон — доработка / рефакторинг

```
Ты работаешь в репо <игра>. Начни с AGENTS.md и docs/INDEX.md.

Цель: <что улучшить и зачем>.
Область: <файлы/каталоги>.
Инварианты: <что должно работать РОВНО ТАК ЖЕ, как сейчас>.
Верификация: существующие тесты зелёные + <новая проверка>.
```

## 8. Рабочий цикл: explore → plan → implement → verify

1. **Explore (только чтение):** «Изучи <модуль> и ответь: где обрабатывается X, что от него зависит. Ничего не меняй.»
2. **Plan:** «Предложи план: шаги, какие файлы затронешь, риски. Код не пиши.» Вы просматриваете план и поправляете. *Планирование дёшево, реализация дорога* — минута на план экономит полчаса отката.
3. **Implement:** «Реализуй по плану, шаг за шагом.»
4. **Verify:** «Запусти тесты/lint, покажи результат. Если есть падения — почини.»
5. **Commit:** маленькие коммиты, один на логический шаг, conventional-сообщения.

В Agent Mode это работает напрямую: агент исполняет bash в песочнице, запускает тесты, показывает вывод — и чинит падения сам.

## 9. Длинные сессии: компактация и сохранение состояния

- В Arena AI длинный чат **автоматически компактируется**: ранняя часть разговора заменяется саммари. Детали (точные имена файлов, договорённости, промежуточные решения) в саммари теряются.
- **Храните состояние в файлах, а не в чате.** Для длинной задачи попросите агента вести `docs/STATUS.md` (или файл задачи): что сделано, что дальше, ключевые решения, какие файлы уже изменены. Тогда даже в **новом** чате агент «подхватывает» задачу, прочитав один файл.
- Чувствуете, что агент начинает «глупеть» (теряет договорённости, повторяет ошибки) — **закрывайте чат и начинайте новый** с промптом: «Прочитай `docs/STATUS.md` и AGENTS.md, продолжи задачу…».
- **Правка поверх провала дороже чистого старта.** Несколько итераций «нет, не так, а вот так» засоряют контекст. Лучше откатить изменения (git) и начать новый чат с чётким описанием проблемы и того, что не сработало.

## 10. Петля улучшения: репо учится на ошибках агента

1. **Каждая поправка агента → правило в `AGENTS.md`/доке.** Не «делай иначе» в чате, а исправление контекста, который привёл к ошибке.
2. **`Gotchas`** в `AGENTS.md` — топ «мин» проекта (максимум 10 пунктов; всё остальное — в доках подсистем).
3. **Периодически чистите `AGENTS.md`:** удаляйте правила, которые теперь держит линтер; которые агент и так соблюдает; дубли из README. Хороший AGENTS.md короткий; плохой — хуже, чем никакой.
4. **Один источник правды:** факт в двух местах → оставляем одно, второе превращаем в ссылку.

## 11. Специфика игр

**Главное ограничение:** агент не видит игру, не слышит звук, не оценивает feel. Поэтому:

- **Headless-верификация — главный рычаг.**
  - Godot: `godot --headless -s tests/smoke.gd`, юнит-тесты на игровую логику.
  - Unity: PlayMode-тесты в batch-режиме (`dotnet test`).
  - Unreal: юнит-тесты C++ (Runtime/UnitTests).
- **Делайте логику тестируемой:** игровая логика (бой, инвентарь, путь) — чистый код без вызовов движка; сцены/UI — тонкий слой. Тогда «сломано в игре» переводится в **assertion**: тест, который падает до фикса и проходит после.
- **Пингуйте версию движка** (в Stack-таблице `AGENTS.md` и файле проекта). Полу-мигрированная кодовая база (старый API рядом с новым) путает агента — доводите миграции до конца.
- **Ассеты:** Godot — `.tscn`/`.tres` текстовые, ок; выгрузки/кэш — в `.gitignore`. Unity — `.meta` не удалять (правило в Never); сборки — никогда. Unreal — агенту лучше работать с C++; Blueprints описывать контрактами в доках как «чёрные ящики».

## 12. Чек-лист: «репо готово к работе с агентом»

- [ ] `AGENTS.md` в корне: ≤ 150 строк, точные команды, версии, границы, Gotchas, Definition of Done.
- [ ] `docs/INDEX.md` — оглавление доков (≤ 60 строк).
- [ ] Доки ключевых подсистем: 50–150 строк каждая, «что / контракты / грабли».
- [ ] Тесты запускаются в песочнице, команда есть в `AGENTS.md`.
- [ ] В репо нет бинарников, сборок, generated-файлов.
- [ ] Комментариев минимум (только «why»); правило записано в `AGENTS.md`.
- [ ] Файлы < 300–500 строк (большие — с обоснованием).
- [ ] Границы Always / Ask first / Never.
- [ ] Нет дублей доки (один источник правды).
- [ ] `docs/STATUS.md` ведётся для длинных задач.

## Приложение: источники

- [AGENTS.md — стандарт инструкций для coding-агентов](https://agents.md) (Jules, Copilot, Cursor, Codex, Zed, Aider, Devin и др.; 60k+ примеров).
- Augment Code, *«How to write good AGENTS.md files»* (18.06.2026): 100–150 строк + референсы — пик эффекта, дальше эффект уходит в минус; ловушка переисследования (−25% к полноте при расплывчатой архитектуре); не более 10–15 ссылок в одном файле.
- Anthropic, *«Best practices for Claude Code»* (code.claude.com/docs): explore → plan → code; верификация — главный рычаг; «over-specified CLAUDE.md»; курс-коррекция рано и часто.
- Community-практика (shanraisshan/claude-code-best-practice): «dumb zone» ~30–40% контекста; rewind/новый старт лучше правки поверх провала; подчинённые агенты для «грязного» исследования.
- Marmelab, *«Agent Experience»* (21.01.2026): комментировать «какую проблему решает код», а не «что он делает»; дробить большие файлы; агенты сами любят закомментировать лишнее — запрещать явно; искать существующий код до написания нового.
- Arena AI: [How to use Agent Mode](https://help.arena.ai/articles/5432423882-how-to-use-agent-mode); [Product Changelog](https://arena.ai/company/product-changelog) — 26.08.2026: интеграция GitHub в Agent Mode (коммиты, пуши, PR, панель диффов).
