# Экспертная оценка решений по доработке M1 «Хворост»

**Рецензент:** техлид проекта
**Предмет:** `EXPERT_B.md`, `EXPERT_C.md` (задание: визуал, карта, кинематографичность, полноценный ИИ крысы, цикл смерти)
**База сверки:** `doc/project-map.md` → `doc/campaign.md` (§1, §7.1, §13, §15) + фактический код `app/`
**Метод:** каждый содержательный тезис обоих документов проверен по коду; спорные места — воспроизведены в одноразовом симуляторе ядра (harness удалён, дерево чистое).

## 0. Ключевой результат ревизии (прочитать первым)

**Оба эксперта ошибочно диагностировали причину «крыса уходит в дозор». Оба предложенных патча ИИ не устраняют баг.**

Реальная причина — не эвристика `OVERWATCH`, а **отсутствие состояния тумана войны у стороны, которая появляется на поле уже после создания ядра**.

`app/packages/core/src/kernel.ts`:

```ts
const owners = [...new Set(state.entities.filter((e) => e.owner > 0).map((e) => e.owner))]; // 175 — вычисляется ОДИН раз
const fog: FogState = createFogState(state, owners);                                         // 176
const revealAllFog = (): void => { if (!fogDisabled) return; for (const owner of owners) … };// 190 — только owners
const refresh = (): void => { refreshFog(fog, state, owners); revealAllFog(); };             // 213 — только owners
```

М1 стартует **без единого врага** (`enemies: []`, единственная крыса — `scripted: true`), поэтому `owners == [1]`. Когда крыса появляется через `spawnScripted`, `fog[2]` не создаётся никогда: `spawnScripted` (1168) и `restoreMatch` (1148) не расширяют множество сторон. Дальше по цепочке:

| Что ломается | Где | Следствие |
|---|---|---|
| `visibleTo(2, mikula)` → `false` | `kernel.ts:226` (`fog[owner]` не существует) | Навь **слепа** |
| `getVisibleCells(2)` → пустое множество | `ai.ts:130` | `foes == []` |
| `getHitPreview(крыса → Микула, "teeth")` → `available: false` | `kernel.ts:1096` `if (!visibleTo(...)) return { available: false }` | скриптовый удар **невозможен** |
| `resolveAction` для `kind:"attack"` падает в `approachStep` | `prologue-script.ts:180` | вместо атаки — попытка сближения |
| `getReachable` считает путь по `knownEntitiesForPath(2)`, где Микулы нет | `kernel.ts:234`, `pathfinding.ts:247` | лучшая клетка — **сама клетка Микулы** |
| `MOVE` в занятую клетку → `apply` вернул `ok:false, reason:"OCCUPIED"` | `occupancy.ts` / `kernel.ts` | ход Нави обрывается, крыса не делает ничего |

А если скриптовая очередь всё же исчерпана, `pickEnemyCommand` при пустых `foes` не находит ни атаки, ни хода и падает в нормативную заглушку (`ai.ts:141`) — **тот самый «дозор», на который жалуется заказчик**. Оба симптома — одна причина.

**Воспроизведено:** harness на ядре с реальной раскладкой М1 (`seed 701`) — 8 раундов подряд:

```
ROUND 0: mikula(19,3) hp=8 | rat=(18,2) hp=4 ap=2 ow=false
  DBG visible(2).size=0                                   ← туман стороны Нави отсутствует
  DBG hitPreview(rat->mikula)={"available":false,...}
  ENEMY cmd rejected: {"type":"MOVE","to":{"x":19,"y":3}} reason=OCCUPIED   ← клетка Микулы
ROUND 1..7: то же самое, урона нет
```

**Проверка гипотезы:** после регистрации стороны 2 в тумане (`restoreMatch` с fog для owner 2) та же сцена даёт:

```
ROUND 0: ENEMY ATTACK :: COMBAT_RESOLVED:MISS     ← скриптовый forceMiss, как в §7.1.6
ROUND 1: ENEMY ATTACK :: COMBAT_RESOLVED:MISS
ROUND 2: ENEMY ATTACK :: COMBAT_RESOLVED:MISS
ROUND 3: ENEMY ATTACK :: COMBAT_RESOLVED:MISS
ROUND 4: ENEMY ATTACK :: COMBAT_RESOLVED:HIT      ← честные кости, Микула 8→5 HP
ROUND 5: ENEMY ATTACK :: COMBAT_RESOLVED:HIT
reachable(rat) includes mikula cell? false
ow=false (дозора нет вообще)
```

То есть **минимальное исправление — ~6 строк в `kernel.ts`**, а не переписывание ИИ. Ни в одном из двух документов об этом нет ни слова.

**Второй системный дефект, на котором построен план C:** `spawnScripted` **выбрасывает** события появления.

```ts
spawnScripted: (unitId, owner, pos) => {
  const events: GameEvent[] = [];
  const spawned = spawnAt(source, unitId, pos, "SUMMON", events);  // events заполняется…
  if (spawned) { …; emit(); }                                       // emit() события не возвращает
  return spawned;                                                   // …и теряется
}
```

`ENTITY_SPAWNED` генерируется (`kernel.ts:467`), но наружу не отдаётся: публичный канал ядра — только `apply()`. У `TacticsKernel` нет подписки на события (`subscribe(listener)` — пинг «состояние изменилось», без аргументов). Утверждение C «Событие `ENTITY_SPAWNED` уже генерируется ядром при `spawnScripted`. Нужно только пробросить его в `BattleScreenView`» — **неверно**: пробрасывать нечего, канала нет. На этом premis'е построены §3.4.1, §3.5.1, §3.5.2, §3.6 документа C.

## 1. Эксперт B

### 1.1. Сильные стороны

1. **Лучшая проработка визуала.** Три законченные функции рисования (`drawMikulaPeasant`, `drawForestRat`, `drawStickItem`) с силуэтной детализацией, читаемой на 52 px: клиновидная морда, сегментированный хвост, уши, горящие глаза, суковатая дубина в руке. Это единственное решение, которое реально «оденет» М1.
2. **Вариант Микулы по экипировке** (`weaponId === "club"` → дубина в руке) — прямо отвечает на «до/после подбора».
3. **Правильный слой для катсцены.** `playCinematicSequence` внутри `createFieldRenderer` на существующем `tween()` наследует автоматически:
   - схлопывание при «уменьшить движение» (этап 1.7, `field-renderer.ts:2432`),
   - деление длительностей на множитель скорости боя (этап 2.10, `tween`: `duration = ms / speedScale`).
   Это ровно то, что теряет решение C.
4. **Затемнение тоже на `tween`** (`fadeScreen` в холсте, а не DOM) — уважает те же настройки и не конфликтует с z-слоями `battle.css`.
5. **Правильно переиспользует существующие примитивы камеры:** `tween`, `easeInOut`, `trainingGlideOffset`, `mapPlane()`, `userMoved` — не изобретает математику подводки.
6. **Блокировка ввода на время сцены** (`lockInput`) — необходимая вещь, которой нет сейчас.
7. **Режиссура по шагам с таймингами** (§7) —最接近 к «кинематографичности» из задания: Микула → палка → удержание → возврат → передача управления.
8. Верно замечает, что дозор для юнита с `range: 1` тактически бессмысленен (эвристика действительно спорная — но см. слабые стороны).

### 1.2. Слабые стороны

1. **Критично: неверная диагностика бага крысы.** Запрет `OVERWATCH` для `category === "melee"` не лечит причину: при пустых `foes` `bestAttack`/`bestMove` вернут `null` и без дозора, крыса просто будет молча завершать ход. Симптом сменится с «стоит в дозоре» на «ничего не делает» — заказчик этого не просил.
2. **Критично: код не компилируется и деградирует молча.** `kernel.getWeaponDefinition(actor.weaponId)` — несуществующий метод: в интерфейсе `TacticsKernel` (`kernel.ts:42–74`) только `getSkillDefinition`. Грей по `packages/core/src` + `packages/render/src` даёт **0 вхождений** `getWeaponDefinition`. С защитным `kernel.getWeaponDefinition ? … : null` ветка молча превращается в «дозор запрещён всегда».
3. **Критично: половина «цикла смерти» нереализуема.** B нигде не вызывает `session.saveBattleCheckpoint()` — восстанавливать нечего. Поле `checkpoints: [{ id: "rat_spawn", onKey: "stick" }]` в JSON5 — **мёртвые данные**: `checkpoints` есть в Zod-схеме (`schemas.ts:474`) и не читается ни одним рантайм-модулем (проверено грепом по всему `packages`). Не затронуты `checkpointArmed()` и `shouldRestoreCheckpoint()` (`prologue-run.ts`), то есть `afterPrologueApply` по-прежнему выставит `outcome = "defeat"`, а строка `if (next.outcome !== "ongoing") setPrologueCard("outro")` в `BattleScreenView.tsx` стоит **вне** `else`-ветки — игрок увидит карточку поражения *до/под* затемнением.
4. **`animateEntityRunIn` содержит ошибку и идёт против устройства рендерера.** Обратный перевод пикселей в клетки выполнен неверно: `centerOf` — это `PAD + x·C + C/2`, а B пишет `(curX - PAD) / CELL_SIZE` — потеря половины клетки по обеим осям. При этом в рендерере уже есть идиома: `ENTITY_MOVED` интерполирует **дробные координаты сетки** напрямую (`shown.x = a.x + (b.x - a.x) * t`, `field-renderer.ts:2755`) — никакого пиксельного round-trip не нужно. Плюс метод не выставляет `holdDisplay`, а `update()` каждый раз перезаписывает `display` из снимка (`field-renderer.ts:3060`), и пост-дрейн в `drain()` (`2821`) сбросит позицию. Анимация будет прерываться.
5. **Параллельный словарь камеры.** В `camera.ts` уже есть `CameraCueKind = "panTo" | "panThreat" | "panReturn"`, `CameraCue { kind, point, durationMs }`, `createCameraDirector`, `enqueueCameraCue`, `beginCameraCue`, **`skipCameraCue`**, `finishCameraCue` — с существующим тестом `render/tests/camera-director.test.ts`. B вводит рядом `CinematicCue` с другим набором (`panTo | zoomTo | trackEntity | screenFade`) и другим полем цели (`target` вместо `point`) — дублирование вместо расширения, и теряется уже готовый `skipCameraCue`.
6. **Расхождение с каноном карты.** B добавляет `W` (валун: `tile.blockLOS = true`, а `edgeCost` и `canFinish` возвращают ∞ — то есть блокирует и проход) и `c` (полуукрытие как сущность-препятствие), хотя `campaign.md` §7.1 прямо фиксирует: «Туман / ямы / укрытия: выключены», а §15.2 требует короткой линейной первой карты. Размер меняется с задокументированных 20×6 на 20×7 без правки `campaign.md` — нарушение правила «одна тема — один файл» (`doc/README.md`).
7. **Не учтён `owner === 0`.** `drawToken` рисует faction-подставку **до** вызова `CLASS_ART` (`field-renderer.ts:1337–1351`), причём для любого `owner !== 2` — круг дружины. Палка получит янтарное кольцо дружины под собой. B это не заметил; C — заметил.
8. **Нарушение дисциплины «уменьшить движение».** `drawStickItem` пульсирует от `performance.now()`, тогда как весь динамический слой использует нейтральную фазу `motionNow = reducedMotion ? 12000 : now` (`field-renderer.ts:1738`). Искры будут мигать при включённой системной настройке.
9. **Нет пропуска катсцены** (закон пролога §1.8: скип есть всегда) и нет телеметрии `skip_cutscene_rate` (§13.9).
10. **Правка `prologue_bestiary.json5` — холостая.** `teeth` уже `category: "melee", range: 1`, дальнобойных умений у крысы нет: менять нечего.
11. `CLASS_ART` типизирован как `(ctx: TokenCtx) => void`; передача вторым параметром `entity` потребует смены типа всей таблицы — B об этом не упоминает.

### 1.3. Оценка

**50 / 100**

*Обоснование:* сильнейший визуал и верно выбранный слой исполнения камеры (рендерер + `tween`, с наследованием reduced-motion и скорости боя), но два из четырёх gameplay-требований задания не решены: ИИ крысы промах мимо причины, а схема чекпоинта не имеет стороны сохранения и не предотвращает показ экрана поражения. Плюс спецификационные расхождения по карте и счётный дефект в анимации вбегания.

## 2. Эксперт C

### 2.1. Сильные стороны

1. **Лучшая культура работы с чужим кодом.** Каждый тезис привязан к файлу и проверен: содержимое `CLASS_ART` (действительно нет `mikula_peasant`, `forest_rat`, `stick`), заглушки `camera.ts` действительно не используются в `field-renderer.ts`/`BattleScreenView.tsx` (только в тесте `camera-director.test.ts`), `checkpointArmed()` действительно не покрывает М1, все клетки `z = 1` (`heightMix: { z0: 0, z1: 1, z2: 0 }`), маркер `t` действительно не порождает сущность. Фактическая база C заметно надёжнее.
2. **Правильно держит ограничения миссии:** «не добавлять ямы и стены — по сценарию М1 они выключены», палка остаётся ≥18 клеток от Микулы (§15.2), точка появления крысы у края. B здесь ошибается, C — нет.
3. **Декларативная схема катсцен** (`cutscenes` в конфигурации миссии + триггеры `missionStart | onSpawn | onFlag | onPickup` + Zod-схема) — ровно то, что просит заказчик: «не хардкодить, а реализовать системно для последующих миссий». У B последовательность М1 захардкожена в UI-коде (§7).
4. **Единственный заметил `owner === 0`** (§1.2.5): палке не нужна faction-подставка. Реальный, подтверждённый кодом дефект.
5. **Верная точка вставки чекпоинта:** `ratSpawned` в `PrologueRunState` + расширение `checkpointArmed()`; сохранение через существующие `session.saveBattleCheckpoint()` / `hasBattleCheckpoint()` — все три метода реально существуют в публичном интерфейсе сессии.
6. **Тонкое и верное наблюдение** (§5.2.3): при активном чекпоинте `outcome` обязан остаться `"ongoing"`, иначе сработает `setPrologueCard("outro")`, которая вызывается вне `else`-ветки `shouldRestoreCheckpoint`. Это единственный способ избежать вспышки экрана поражения.
7. **Порядок реализации** (визуал → карта → ИИ → чекпоинт → катсцены) с корректными зависимостями.

### 2.2. Слабые стороны

1. **Критично: патч ИИ — доказуемый no-op, причём с обратной логикой.** Предложено `if (foes.length === 0 && watcher) return OVERWATCH`. В аварийном состоянии `foes.length === 0` (туман стороны Нави отсутствует) — условие истинно, крыса **по-прежнему уходит в дозор**. Хуже того: дозор сохраняется ровно в той ситуации, где он является багом, и отключается там, где он — legitimate тактика («противник жив, но действий нет»).
2. **Критично: весь триггерный слой катсцен построен на неверной предпосылке.** `ENTITY_SPAWNED` для скриптовых появлений **недоступен** (см. §0): `spawnScripted` выбрасывает события, API подписки на события у ядра нет. Следовательно §3.4.1 (п.2), §3.5.1, §3.5.2, §3.6 не реализуемы в предложенном виде.
3. **Слой исполнения слабее, чем у B.** `updateCamera(state, dt, world, screen)` на покадровом тике обходит существующие `tween()`/`wait()` → теряется схлопывание при `reducedMotion` (этап 1.7) и множитель скорости боя (этап 2.10). Пропуск катсцены (`skipCameraCue` уже есть в `camera.ts`) в модели C не предусмотрен, хотя закон §1.8 требует скип.
4. **Затемнение — антипаттерн для этого кода.** Вложенные `setTimeout(800)`/`setTimeout(400)` + CSS-транзишен: не учитывают скорость боя и reduced-motion, не очищаются при размонтировании, а `z-index: 100` вклинивается в собственную слоистость `battle.css`. Вариант B (затемнение на `tween` внутри холста) корректнее.
5. **Избыточный параллельный механизм восстановления.** `checkpointRestoreRequested` дублирует уже работающий контур `shouldRestoreCheckpoint` → `restoreBattleCheckpoint` → телеметрия `death_by: "checkpoint"` (он станет работать для М1 сразу после добавления `ratSpawned` в `checkpointArmed`). И он опаснее: при отсутствующем чекпоинте связка «Мёртвый Микула + `outcome: "ongoing"`» даёт софт-лок (нет бойцов, миссия не завершена).
6. **Декор: решение ищет не там.** Утверждается, что кустов нет и их надо рисовать из маркеров `t`. На самом деле `drawTile` **уже рисует 1–2 кустика на каждой клетке** (кроме ям и валунов), плюс редкий декор биома (~3 % клеток) и камешки-осыпь на перепадах ярусов (`field-renderer.ts:1165–1210`). Ощущение «плоскости» создаёт однообразный `z = 1`, а не отсутствие растительности. Массив `decor` + правки рендерера дадут минимум визуальной пользы на максимальную сложность.
7. **Ошибки в предложенных данных.** Пример раскладки внутренне противоречив: заявлено «~22×10», приведено 7 строк; строки разной длины (22 и 20 символов); `M` в итоге на `x = 2`, а не `x = 1`. Символы `0/1/2` конфликтуют с `pushMarker` (любой символ вне `. P W E c` становится маркером, `prologue-layout.ts:82`) — C это оговаривает, но в примере цифры всё равно попадают в строки с содержимым. `heightMix` предлагается обновить, хотя при наличии `layout` его не читает никто (`createPrologueMatch` работает только от `compilePrologueLayout`).
8. **Локализация не упомянута вовсе**, а `scripts/visual-audit.mjs` (входит в `pnpm check:versions`) **валит сборку при расхождении путей ключей RU/EN**. Любой новый текст — это правка двух файлов.
9. **Нарушение слоёв.** Тип катсцен предлагается в `core/types.ts`, Zod-схема — в `content/schemas.ts`; но у `content` зависимости `{ json5, zod }` — он не может импортировать `core`. Типы будут молча дублироваться.
10. Анимация вбегания сводится к «смещению от края карты» без указания механизма, совместимого с `holdDisplay` и послена́дровым сбросом `display`.

### 2.3. Оценка

**58 / 100**

*Обоснование:* самая аккуратная фактическая база, верная архитектура данных (декларативные катсцены в контенте), верная точка вставки чекпоинта и единственное верное замечание про `outcome: "ongoing"`; удержаны канонические ограничения карты. Снимают баллы: no-op-патч ИИ, нереализуемый триггерный транспорт, более слабый слой исполнения (потеря reduced-motion/скорости/скипа), дублирующий и небезопасный механизм восстановления, отсутствие плана локализации.

## 4. Рекомендуемый подход: гибрид «данные от C — исполнение от B — ядро с нуля»

Ни один из документов не годится как план целиком. Собирается третий:

| Задача | Чей подход | Почему |
|---|---|---|
| Схема катсцен в контенте, триггеры, `lockInput`, `skippable` | **C** | Отвечает на «не хардкодить, системно» |
| Словарь камеры, `skip`, очередь кью | **C + B**, но на базе существующего `camera.ts` | Не дублировать `CameraCueKind`; `skipCameraCue` уже есть |
| Исполнение панов/удержаний/затемнения | **B** | `tween()` даёт reduced-motion + `speedScale` |
| Анимация вбегания | **Ни тот, ни другой** — `lunges` + дробные координаты сетки | Обходим `holdDisplay` и сброс в drain() корректно |
| Art трёх сущностей | **B** + правка `owner === 0` от C | — |
| Рельеф карты | **Новый минимальный вариант**: параллельный `heights`, без ям/укрытий | Не конфликтует с `pushMarker`, держит §7.1/§15.2 |
| ИИ крысы | **Новый**: исправление тумана в ядре | Единственное, что реально лечит баг |
| Чекпоинт и восстановление | **Ядро — C, затемнение — B**, через существующий контур | Без дубль-флагов и софт-локов |

## 5. План итоговой реализации

### Этап 0. Ядро: стороны, появляющиеся по ходу боя (блокирующее исправление)

**Файл:** `app/packages/core/src/kernel.ts`

1. Заменить замороженный `owners` живым вычислением:
   ```ts
   const activeOwners = (): number[] =>
     [...new Set(state.entities.filter((e) => e.owner > 0).map((e) => e.owner))].sort();
   ```
   Использовать в `refresh()` → `refreshFog(fog, state, activeOwners())` и в `revealAllFog()`.
2. В `createFogState` — создавать запись для каждой стороны, присутствующей в снимке; в `restoreMatch` — доcоздавать отсутствующие записи из `restoredFog` (сейчас ключ создаётся, но `refreshFog` его не обслуживает).
3. Не трогать семантику тумана: при `fogDisabled` `revealAllFog()` по-прежнему раскрывает всё, теперь и для стороны 2.

**Эффект:** крыса видит Микулу → скриптовый `forceMiss` исполняется как задумано → дальше честный ИИ: сближение и укусы 2–3 урона. `getReachable` перестаёт выдавать занятые клетки. Дозор исчезает сам.

**Тест** `packages/core/tests/prologue-sim.test.ts`:
- крыса атакует в каждый свой ход, первый результат — `MISS` (скрипт), далее честные броски;
- в М1 ИИ **никогда** не выдаёт `OVERWATCH` и не выдаёт команду, которую ядро отвергает (прогон по 20+ сидам);
- после гибели Микулы при `ratSpawned` — `shouldRestoreCheckpoint(...) === true`.

**Дополнительная страховка (отдельным коммитом, только если тест покажет нужду):** явное правило «юнит ближнего боя в контакте с видимым противником не тратит последнее ОД на дозор». Принимать **не** как лечение бага, а как тактическую правку с собственным тестом.

### Этап 3. Кинематографичность

**3.1 Транспорт событий появления (предпосылка для триггера `onSpawn`)**

`kernel.ts` — не терять события `spawnScripted`: копить их в буфере ядра и отдавать через `drainSpawnEvents(): GameEvent[]` (альтернатива — возвращать `{ entity, events }`, но это ломает существующих вызывающих). `prologue-run.ts` (`spawnUnits`) складывает их в `PrologueRunState.pendingEvents`; `BattleScreenView` проигрывает их существующим `renderer.play(...)` рядом с событиями команды.

Побочный выигрыш: у всех скриптовых появлений пролога (М2 — волна крыс, М3 — упыри, М4 — знахарка) появляется положенный эффект `ENTITY_SPAWNED`. Затронут сетевой формат — **обновить `doc/network-protocol.md`**.

**3.2 Данные — `packages/content/src/schemas.ts`**

```json5
cutscenes: [
  { id: "m1_intro",
    trigger: { kind: "missionStart" },
    lockInput: true, skippable: true,
    steps: [
      { kind: "focus", target: { configId: "mikula_peasant" }, holdMs: 500 },
      { kind: "pan",   target: { marker: "S" }, durationMs: 900, holdMs: 700 },
```

- Схема Zod — `strict()`, с перечислением `kind` и валидацией «ровно один источник цели».
- Тип рантайма брать как `z.infer<>` из `content` — **не** дублировать в `core/types.ts` (`content` не зависит от `core`, а ядро — только правила).

**3.3 Камера — `packages/render/src/camera.ts` (расширение, не замена)**

- Оставить `CameraCueKind`, добавить `hold | fade`; `CameraCue.target` — размеченное объединение: `point | { cell } | { configId } | { marker }`.
- Оставить и покрыть тестами `createCameraDirector` / `enqueueCameraCue` / `beginCameraCue` / `skipCameraCue` / `finishCameraCue` — скип получается бесплатно (§1.8).
- `resolveCueTarget(cue, view, layoutMarkers)` — чистую функцию в `camera.ts` с юнит-тестами (пакет `render` не зависит от PixiJS в этой части).

**3.4 Исполнение — `packages/render/src/field-renderer.ts`**

- `playCinematic(sequence): Promise<void>` и `fadeScreen(mode, ms, color)` **на существующем `tween()`** (вариант B): наследуем схлопывание при `reducedMotion` и деление на `speedScale`.
- `fadeScreen` пишет в отдельный `Graphics` выше `atmosphere`; при `reducedMotion` — мгновенно.
- `setInputLocked(locked)` на рендерере **и** флаг `cutscenePlaying` в `BattleScreenView` (блокировка `onCell`, `endTurn`, кнопок панели) — две раздельные поверхности ввода, нужны обе (жесты холста у B, React-панель у C).
- **Вбегание:** тween'ить существующий `lunges.set(id, { dx, dy })` (уже применяется в `entityPixel` и очищается в конце `drain`) от смещения за край карты к `{0,0}`; запускать внутри `play()`, где `holdDisplay` уже выставлен. **Не** использовать пиксельный round-trip из B.

**3.5 Интерфейс — `packages/ui/src/BattleScreenView.tsx`**
