# Запуск, сборка и публикация

Предмет ведения: среда разработки, команды, проверка, GitHub Pages и установка PWA. Правила игры и устройство модулей не входят.

Реализация: `app/` (pnpm), `.github/workflows/deploy-pages.yml`, `app/apps/game-pwa/vite.config.ts` (`BASE_PATH`).

---

## 1. Среда

| Состав | Минимум |
|---|---|
| Система | Windows 10 1903+ x64; также macOS/Linux |
| Обозреватель | Chrome 120+ или Edge 120+ |
| Node.js | 20 LTS (64-bit) |
| pnpm | 9 или 10 (Corepack) |
| Диск | ≥ 1 ГБ свободно |

Права администратора — только на установку Node.js.

### 1.1. Node.js (Windows)

1. Скачать **20 LTS** x64 с [https://nodejs.org/](https://nodejs.org/).
2. Установить с отметкой `PATH`. Открыть **новое** окно PowerShell:

```powershell
node -v
npm -v
```

При отказе «running scripts is disabled»:

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

### 1.2. pnpm

```powershell
corepack enable
corepack prepare pnpm@10.34.5 --activate
pnpm -v
```

Версия закреплена полем `packageManager` в `app/package.json`. Если Corepack
показывает другую версию, повторите команду выше; это снижает риск отличий
в lockfile и поведении workspace-команд. Если `corepack` недоступен:
`npm install -g pnpm@10.34.5`.

## 3. Команды

| Команда | Назначение |
|---|---|
| `pnpm dev` | Сервер разработки (`http://127.0.0.1:5173/`) |
| `pnpm test` | Автоматические проверки |
| `pnpm typecheck` | Проверка типов |
| `pnpm lint` | Проверка кода (ESLint): **ошибки** роняют сборку, предупреждения — нет (0.20.55) |
| `pnpm lint:fix` | Исправить автоматически поправимое (0.20.55) |
| `pnpm format` | Форматирование Prettier: ширина строки 120 (0.20.55) |
| `pnpm format:check` | Проверить форматирование без правки (0.20.55) |
| `pnpm version:set patch` | Выпустить версию: номер меняется в `app/package.json` и в титуле `doc/README.md` (0.20.54) |
| `pnpm build` | Производственная сборка PWA |
| `pnpm preview` | Просмотр сборки (`http://127.0.0.1:4173/`) |
| `pnpm resize:action-art` | Привести образы действий (`public/actions`) к кадру 512×512 (0.20.48) |
| `pnpm audit:deps` | Проверить зависимости на известные уязвимости; ненулевой код при high/critical (0.21.0). Недоступность реестра npm не считается находкой: попытка повторяется, затем шаг пропускается с предупреждением |

Остановка: `Ctrl+C`. Если порт занят — открывать адрес из вывода сборщика.

Проверка версии и окружения:

```powershell
pnpm check:versions
node --version       # должен быть >= 20
pnpm --version       # должен соответствовать packageManager
```

Команду `check:versions` полезно выполнять до `build` и перед публикацией.

### Что проверяется на каждой ветке (CI, 0.20.55)

`.github/workflows/ci.yml` на каждый push и pull request запускает три задания:

| Задание | Команды | Роняет сборку |
|---|---|---|
| `version-consistency` | `pnpm check:versions` | да |
| `lint` | `pnpm lint`, `pnpm format:check` | да: ошибки линтера и неотформатированные файлы |
| `quality` | `pnpm typecheck`, `pnpm test`, `pnpm audit:deps`¹, `pnpm build` | да |

¹ Шаг аудита внесён в образец `doc/examples/ci.yml`; в боевой
`.github/workflows/ci.yml` его переносит пользователь с правом
`workflows` (см. примечание ниже). Локально аудит работает без ограничений.

Аудит зависимостей (0.21.0) роняет сборку при уязвимостях уровня `high` и
`critical`; `moderate` сборку не роняет. Находки в инструментах разработки
(dev-сервер vitest/vite/esbuild) тоже попадают в отчёт: их закрывают
обновлением dev-зависимостей, а не понижением порога — при введении шага
обновлены vitest до 3.2, vite до 6.4 и esbuild до 0.25, после чего аудит
чист. Локально тот же прогон: `pnpm audit:deps` из каталога `app`.

Аудит ходит в реестр npm, и `pnpm audit` отвечает одинаковым ненулевым
кодом и на находку, и на обрыв связи (`ERR_SOCKET_TIMEOUT`, 5xx, отказ
DNS) — из-за этого ветка падала на недоступности registry.npmjs.org при
исправных зависимостях. Поэтому шаг идёт через `scripts/audit-deps.mjs`:
он разбирает машинный отчёт `pnpm audit --json` и роняет сборку только по
реальным находкам порога, а сетевой отказ повторяет трижды с паузой и,
если реестр так и не ответил, завершается успешно с предупреждением в
журнале. Проверить оба исхода локально можно, подменив `pnpm` в `PATH`.

Рабочие процессы лежат в ветке: `.github/workflows/ci.yml` и
`deploy-pages.yml` отслеживаются git. Образец `doc/examples/ci.yml`
хранится как копия для ручной установки в другие репозитории и
поддерживается в соответствии с боевым файлом.

> **Право `workflows`.** Приложение Arena не имеет права `workflows` и
> не может отправить в ветку изменение `.github/workflows/*.yml`: шаг
> аудита (0.21.0) уже внесён в образец `doc/examples/ci.yml`, а в боевой
> файл его переносит пользователь с этим правом — скопировать 6 строк
> шага `Audit dependencies` или файл целиком. До переноса аудит
> выполняется локально (`pnpm audit:deps`).

Прежде на ветках проверялась только согласованность версий, а типизация и
тесты запускались лишь при публикации в `main` — регрессию было видно
слишком поздно.

Предупреждения линтера сборку не роняют: исторический код (неиспользуемые
переменные, последовательные `await` в проигрывателе событий) приводится в
порядок по мере касания файлов, а новый код пишется без новых предупреждений.

### Выпуск версии (0.20.54)

Номер версии объявлен один раз — в `app/package.json`. Увеличивается одной
командой из каталога `app`:

```powershell
pnpm version:set patch      # 0.20.54 → 0.20.55 (по умолчанию)
pnpm version:set minor      # → 0.21.0
pnpm version:set 0.21.0     # явный номер
```

Команда правит корневой манифест и титул `doc/README.md`; больше ничего
менять не требуется:

- внутренние пакеты и приложения версии не объявляют вовсе (они приватны),
  поэтому расхождение манифестов невозможно;
- `CORE_VERSION` и `APP_VERSION` выводятся из номера
  манифеста через `app/packages/core/src/version.ts`; формат журнала
  повтора (`REPLAY_FORMAT_VERSION`) и версия боевых правил
  (`RULES_VERSION`), как и `SAVE_FORMAT_VERSION`, от номера приложения
  независимы — инкрементируются осознанно при смене формата или правил;
- тесты версий сверяются с манифестом, а не с литералом, и при выпуске не
  правятся.

`pnpm check:versions` удерживает правило: лишняя версия в дочернем
манифесте, литерал версии в исходнике (`packages/*/src`, `apps/*/src`) и
расхождение с документацией — ошибка. В тестах номер может встречаться по
делу (снимки сохранений прежних версий, номера форматов), поэтому они
проверке не подлежат.

Новые образы действий и умений кладут в `app/apps/game-pwa/public/actions` и приводят к кадру 512×512 командой `pnpm resize:action-art` (нужен ImageMagick; генератор отдаёт 1024×1024, лишнее дешевле убрать в каталоге, чем отдавать обозревателю). Имя файла совпадает с идентификатором оружия, умения или служебного действия; запись в карте `app/packages/ui/src/action-art.ts` обязательна — тест проверяет обе стороны.

## 4. Проверка перед работой

После `pnpm install`:

```powershell
pnpm test
pnpm typecheck
pnpm dev
```

Ожидание в обозревателе: загрузка → главное меню; «Быстрый матч» доступен; при сохранённой былине есть акцентная «Продолжить». Автоматические проверки должны пройти до ручной проверки оболочки.

Производственная сборка: остановить `dev`, выполнить `pnpm build` и `pnpm preview`, повторить те же шаги меню и быстрого матча.

## 6. Публикация на GitHub Pages

Рабочий процесс уже в репозитории: `.github/workflows/deploy-pages.yml`. Шаблон в `doc/` не хранится.

Разовая настройка:

1. Pages доступен для публичных репозиториев (или GitHub Pro для частных).
2. **Settings → Pages → Source → GitHub Actions**.
3. Слить в `main` или запустить **Actions → Deploy PWA to GitHub Pages**.
4. Адрес: `https://<владелец>.github.io/<репозиторий>/` (этот репозиторий: `https://aleksandrrv.github.io/bylina_tactics/`).

Workflow: `push` в `main` → pnpm + Node → `pnpm test` → сборка с `BASE_PATH=/<репозиторий>/` → выкладка `app/apps/game-pwa/dist`. Имя репозитория подставляется автоматически.

Локальная проверка той же сборки:

```bash
cd app
BASE_PATH=/bylina_tactics/ pnpm build
# PowerShell: $env:BASE_PATH="/bylina_tactics/"; pnpm build
pnpm preview
```

Открыть `http://localhost:4173/bylina_tactics/`.

## 7. Установка на телефон

PWA кэширует оболочку service worker (`vite-plugin-pwa`, `registerType: autoUpdate`). Нужен один заход по HTTPS. Одиночные режимы (быстрый матч, кампания, обучение) работают без сети.

**Android (Chrome):** открыть адрес Pages → дождаться меню → «Установить» в приложении или меню Chrome → значок «Былина». Проверка: авиарежим.

**iPhone / iPad (Safari):** открыть в Safari → «Поделиться» → «На экран Домой». Один запуск с сетью, затем авиарежим. Система может чистить хранилище давно не открытых веб-приложений.

Обновление: после публикации в `main` при первом запуске с сетью. В авиарежиме остаётся прежняя сборка.

## 8. Частые отказы

| Наблюдение | Действие |
|---|---|
| `pnpm` / `node` не команда | Повторить §1 в новом окне; проверить `PATH` |
| Политика сценариев PowerShell | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` |
| `EPERM` при install | Закрыть IDE/браузер, удалить `node_modules`, повторить |
| Пустая страница | Console (`F12`); верный адрес `pnpm dev` |
| `Failed to resolve import "pixi.js"` | `pnpm install` из `app`; см. `app/packages/render/README.md` |
| Чёрное поле, панель есть | Включить аппаратное ускорение (WebGL) |
| Язык сбросился | Не инкогнито; не блокировать `localStorage` |
| Pages 404 | Source = GitHub Actions; дождаться зелёного workflow |
| Нет стилей/портретов на Pages | Сборка без `BASE_PATH` — публиковать только через workflow |
| Chrome не предлагает установку | Нужен HTTPS и дождаться кэша |
| На iPhone нет пункта установки | Открыть в Safari |
| Авиарежим — белый экран | Сначала полностью загрузить меню по сети |

Отладочные кнопки боя описаны в `debug-mode.md`, не здесь.

## Скриншот-регрессия (0.20.27, этап 5.1)

Ключевые состояния (меню, обучение, старт быстрого матча; карта кампании и
итог миссии — при наличии прогресса) снимаются Chromium'ом и сравниваются с
эталонным набором предыдущей версии: незаметное изменение картинки перестаёт
проходить незамеченным.

```powershell
cd app
corepack pnpm preview            # терминал 1 (BASE_URL по умолчанию :4173)
corepack pnpm add -D playwright pixelmatch pngjs
npx playwright install chromium
corepack pnpm screens:capture    # терминал 2: artifacts/screens/<версия>/
corepack pnpm screens:compare    # расхождение кадра > 2% — регресс
```

Эталонный набор хранится вне репозитория (артефакт выпуска); путь к нему
задаётся `BASELINE_DIR`. Допустимый порог расхождения кадра настраивается
`SCREEN_DIFF_THRESHOLD` (доля отличившихся пикселей, по умолчанию 0.02).
