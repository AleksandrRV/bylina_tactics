## 2. План исправлений по патч-версиям

Принцип из `doc/roadmap.md` §1: правки внутри подэтапа поднимают `0.21.x`
и не расширяют объём. Один пункт плана — один коммит; ветка остаётся
рабочей после каждого. Каждая правка сопровождается тестом, который
**падал бы до неё** (норма трека укрепления §3.1).

### 0.21.25 — ложная победа в М2 (P0)

Единственная правка выпуска: исход миссии не должен зависеть от порядка
пяти пересекающихся условий.

1. **Убрать блок 522–530** — тот, что заносит в `extracted` всех
   отсутствующих на поле при любом `ENTITY_REMOVED`. Он и порождает
   ложную победу.
2. **Записывать эвакуацию только по событию.** Оставить единственный
   цикл (497–502), но брать `configId` не из устаревшего снимка `match`,
   а из пары «снимок до применения + событие», и дополнительно
   удостоверяться, что боец **не** отмечен `dead`.
3. **Свернуть пять проверок исхода в одну функцию** `resolveCryOutcome`
   с явным приоритетом, зафиксированным нормативом §7.2 пп. 10–11:
   гибель любого из двоих → `defeat` (или `ongoing` при взведённом
   чекпоинте) **раньше**, чем проверка «оба эвакуированы → `victory`».
   Убрать пустой `if` с комментарием (строки 519–521).
4. Тесты (`prologue-sim.test.ts` + новый блок в `prologue-m2.test.tsx`):
   - гибель Микулы в один пакет с эвакуацией Федота → `defeat`, а не
     `victory` (**этот тест падает на 0.21.24**);
   - оба эвакуированы → `victory`;
   - гибель Федота после освобождения → `defeat`;
   - гибель Микулы после освобождения при взведённом чекпоинте →
     `ongoing` + `shouldRestoreCheckpoint === true`.

Закрывает: **B4, B5, B6, U11**.

## 4. Порядок и риски

Порядок выпусков не произволен: сначала единственный дефект, который
**искажает исход миссии** (0.21.25), затем расхождения с нормативом,
которые видит игрок (0.21.26–0.21.27), и только потом рефакторинг с
тестами (0.21.28) — тот же принцип, которым велся трек укрепления 0.21.

Основной риск — п. 3 выпуска 0.21.25: свёртка проверок исхода трогает
самую нагруженную ветку `prologue-run.ts`. Он закрывается тем, что
четыре теста на исход М2 пишутся **до** правки и первый из них падает на
текущем коде.

После каждого выпуска: `pnpm -r test`, `pnpm -r typecheck`, `pnpm lint`
(включая `check:boundaries`) и `pnpm check:versions`. Номер версии
поднимается через `pnpm version:set` — единственное место объявления
`app/package.json`. Норматив `doc/campaign.md` правкам не подлежит:
все изменения приводят код к нему, а не его к коду. Исключение — п. 1
выпуска 0.21.27, где к нормативу приводятся данные и каталоги.
