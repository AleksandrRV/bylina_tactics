# Архитектура программных модулей

Предмет ведения: границы модулей, направление зависимостей и путь данных. Не содержит игровых алгоритмов, форматов сообщений и макетов экранов.

Реализация: `app/packages/*`, `app/apps/*`. Дерево каталогов — `project-map.md`.

---

## 1. Путь данных

```
Ввод (интерфейс либо поле боя)
        │ команда
        ▼
Модуль сессии ──────── канал связи ────────► прочие участники
        │
        ▼
Тактическое ядро (только у ведущего)
        │
        ├─ состояние ─► хранилище представлений ─► интерфейс
        └─ события ───► шина ─► средство отображения поля
```

Ведущий исполняет правила и рассылает события. Ведомый передаёт намерение и воспроизводит полученные события. Алгоритм управления противником, работающий у ведущего, формирует те же команды, что и человек.

---

## 2. Направление зависимостей

Допустимо зависеть только вниз по списку:

1. `module-content`, `module-i18n`, `module-settings`
2. `module-core-campaign`, `module-core-tactics`
3. `module-storage`, `module-network`
4. `module-session`
5. `module-ui`, `module-render-pixi`

Модули ядер не обращаются к объектной модели документа обозревателя, к библиотеке построения интерфейса, к средству отображения и к каналу связи.

Направление зависимостей и чистота ядер проверяются автоматически: `app/.dependency-cruiser.cjs` объявляет правила `no-cycles`, `layers-point-down` и `core-remains-pure`, а команда `pnpm check:boundaries` (часть `pnpm lint`, отдельный шаг в CI) роняет сборку при нарушении.

## 3. Модули

### 3.1. `module-content`

Загрузка и проверка файлов конфигурации. Внешний доступ — функция получения записи по роду и идентификатору. Состав полей задан документом «Схема конфигурации».

### 3.2. `module-i18n`

Возвращает строку по ключу. Список языков читает из манифеста каталогов. Подписывается на смену языка в модуле настроек. Договор, формат словарей и порядок добавления языка — документ «Локализация».

### 3.3. `module-settings`

Хранение пользовательских предпочтений: громкость, размер шрифта, режим пониженной цветовой различимости, язык. Носитель — локальное хранилище обозревателя. Полный обзор наблюдателя хранится в состоянии сессии.

### 3.4. `module-storage`

Запись и чтение кампании, журнала повтора (начальное значение генератора и последовательность команд) и статистики. Сражение записывается полным снимком ведущего, без сокращения по зрению.

### 3.5. `module-network`

Передача конвертов. Интерфейс транспорта: отправка и подписка на получение. Реализации: канал WebRTC и локальный транспорт для игры на одном устройстве. Подмодуль установления соединения: обмен описанием сессии через изображение быстрого считывания, короткую строку либо ретранслятор. Модуль не интерпретирует содержимое конверта.

Сокращение сведений по зрению выполняет модуль сессии, а не транспорт.

### 3.6. `module-core-campaign`

Конечный автомат Летучего Корабля: запасы, счётчик Тьмы, набор доступных миссий, состав дружины, ранения, окончательная гибель, работы Кузни и Горницы. Читает конфигурацию, отдаёт состояние модулю хранения.

### 3.7. `module-core-tactics`

Исполнительная среда на неизменяемых объектах состояния и генератор с фиксированным началом. Квадратная решётка.

Подмодули:

- поле: массив клеток, поиск пути, расстояние, поправка высоты, линия наблюдения, обзор, занятость;
- бой: попадание, критический удар, укрытие, разрушение, смещение, дозор;
- управление противником: формирование команд.

Вход — команда установленного контракта. Выход — набор событий. Запросы предпросмотра не изменяют состояние и не обращаются к генератору.

### 3.8. `module-session`

Связывает ядра, канал связи и хранение. Ведёт смену экранов и роль участника.

- Ведущий: принимает команду, передаёт в тактическое ядро, применяет набор событий у себя, направляет каждому получателю сокращённый по зрению набор.
- Ведомый: направляет команду ведущему; собственные события не вычисляет.
- Наблюдатель: принимает события и снимки, команд не отправляет.

### 3.9. `module-render-pixi`

Отображает поле по событиям и снимку. Не запрашивает и не изменяет правила. Один знак персонажа соответствует одной клетке.

### 3.10. `module-ui`

Строит элементы управления и направляет команды в модуль сессии. Не вычисляет вероятность попадания, дальность и допустимость: для предпросмотра направляет запрос, описанный в документе «Контракты обмена».

---

## 4. Пример: выстрел ведомого

1. Интерфейс формирует команду атаки.
2. Сессия ведомого передаёт конверт ведущему.
3. Тактическое ядро ведущего проверяет допустимость, изменяет состояние, формирует набор событий.
4. Сессия ведущего отображает набор у себя и рассылает сокращённые копии.
5. Средство отображения ставит набор в очередь воспроизведения. Хранилище представлений обновляет полосы здоровья и очков действия.

---

## 5. Обязательные ограничения

1. Ядра испытываются в среде без обозревателя.
2. Компонент интерфейса не изменяет запас здоровья, очков действия и положение.
3. Изменение баланса выполняется только в файлах конфигурации.
4. Ядро завершает расчёт хода синхронно; воспроизведение изображения не задерживает расчёт.
5. Поле и контракты обмена не содержат сущностей, занимающих несколько клеток.

### Формат сохранений

Постоянные данные кампании хранятся в `localStorage`. Каждая запись содержит `formatVersion`; текущая версия формата — `2`. Запись несёт состояние кампании, экран сессии, необязательный снимок партии, туман войны и необязательный прогресс сюжетной сцены пролога (`prologueProgress`: состояние сценария, сыгранные катсцены, видел ли игрок вступление). Битое поле прогресса снимается при миграции и не роняет всю запись. Модуль `storage` применяет `migrateSave` при чтении и немедленно сохраняет успешно перенесённую запись. Неизвестный будущий формат не загружается. Список повторов хранится тем же носителем и ограничен **20** последними записями.
